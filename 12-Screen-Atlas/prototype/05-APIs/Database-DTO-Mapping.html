Database-first API DTO mapping

Evidence and precedence

The standalone SQL is authoritative effective structure. The derived table catalog documents all 268 tables and exact fields/constraints/indexes/triggers; a private source-chain replay and independent SQL-only install agree across 23 catalog dimensions. See reconciliation.

Structure is validated; application ownership, runtime permissions and API behavior remain proposed. No production records or provider payloads were inspected.

04-Database/Module-Mapping.md identifies candidate schema/module relationships and explicitly does not grant write ownership. 03-Modules/*/LLD.md and 07-Engineering/State-and-Recovery-Contracts.md define proposed command ownership and boundaries. Relevant 06-Workflows/ pages establish cross-module ordering.

API DTO fields remain proposed until the owning module approves the mapping and runtime grants.

DTO mapping rules

  • A database id UUID may be represented by a public ...Id only when the business use and object-level authorization justify it. Internal internal_id and every *_internal_id shadow key are never public DTO fields or authorization references.
  • CamelCase request/response names are API names. They map explicitly to documented columns; they do not automatically mirror ORM/database rows. Fields derived from joins, calculations, signed tokens, or state projections are identified as derived and are not represented as persisted columns.
  • Database row_version is not interchangeable with domain revision counters such as review_version or revision_number. Each precondition is named for its aggregate and source field.
  • Nullability, precision, length, controlled status values, ownership foreign keys, and database checks constrain the proposed DTO. Application policy may be stricter, but it must not weaken a database constraint.
  • Clinical files, OTP digests, password/refresh hashes, provider payloads/secrets, actor IDs, raw audit payloads, deleted flags and soft-delete actors are not exposed just because columns exist.
  • A candidate table is not a write grant. The source file and exact field mapping are linked below; the owning service must approve writes, transaction boundaries, and outbox/audit behavior.
